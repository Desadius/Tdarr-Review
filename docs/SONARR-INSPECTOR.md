# Manual Sonarr episode inspection

The shared settings dialog can save one optional Sonarr URL and API key. The key is stored with the private server settings, is never returned to the browser, and is sent only in the `X-Api-Key` header. Leave the key field blank to keep the stored key. URLs with user information, query strings or fragments are rejected. Saving this draft does not apply settings, enable TV processing or change Movie review state.

After saving, use **Load series** and then **Inspect selected series**. Neither action runs when the dialog opens. Each button makes a new authenticated Review request; there is no polling or cached result. Inspection uses the exact saved settings revision. A stale revision fails and must be reloaded. Review makes only Sonarr `GET` requests for the series list and, for the selected series, EpisodeFile and Episode records from the [Sonarr v3 API schema](https://github.com/Sonarr/Sonarr/blob/develop/src/Sonarr.Api.V3/openapi.json). Redirects, non-JSON responses, malformed arrays and oversized responses fail closed. The limits are 7 seconds per request, 4 MiB for the series list, 16 MiB per selected-series endpoint, and 5,000 series, 20,000 files and 50,000 episodes. Exceeding a limit reports an unavailable/incomplete snapshot; records are never silently dropped.

Only HTTP 200 responses are accepted as complete. The display shows allowlisted titles, safe relative labels, file and episode IDs, explicit linked memberships and Sonarr numbering fields. Episodes Sonarr reports with no file are shown in a separate “without a file in Sonarr” list; this does not assert that a file is missing from disk. It does not reveal Sonarr's private root paths or arbitrary API fields. Episode matching builds one pure index for the complete snapshot and resolves each file against it with a fresh request-scoped namespace. It uses exact paths from that same snapshot; no path translation or filename inference occurs.

The result is explicitly **UNVERIFIED Sonarr metadata**. For one exact mapped EpisodeFile, the manual **Check source path** action makes a fresh request with the saved revision, series ID and EpisodeFile ID. Review fetches a new selected-series Sonarr snapshot, requires the same unambiguous episode binding, and maps Sonarr's canonical path beneath the exact configured `libraries.tv.sonarrRoot` to a relative path under `libraries.tv.mediaRoot`. Component spelling is case-sensitive, including the configured drive letter; prefix lookalikes and traversal are rejected. No browser-supplied file path is accepted.

Only the derived relative path and the configured container root are sent to a fixed Node child process. The child performs filesystem metadata checks for that one path: it rejects symlinked root ancestors or components, containment changes, non-regular files, hard links and unsupported file types. It records stable observations around the check and returns only a safe status, relative label, size and modification time. It never opens or reads media bytes, scans directories, probes codecs, writes files or calls Tdarr. Results distinguish a present file, missing path, unsafe/unsupported path, changed path, busy worker and unavailable check. A timeout returns unavailable; its single worker slot remains occupied until the child is confirmed closed. Shutdown signals the child and waits only for a bounded interval. Movie routes stay in the Review process and remain available while this check runs.

This is metadata evidence, not proof that two paths are the same physical object or that file contents match. Filesystem paths can still change between observations; the checks do not provide an atomic snapshot or protect against every concurrent filesystem mutation. Results are request-scoped and not saved, and cannot be used as approval evidence. `libraries.tv.enabled` remains unavailable. Movies do not depend on this optional connection.

For the same exact EpisodeFile, **Inspect Tdarr result** is a separate explicit, read-only action. It re-fetches the Sonarr binding and saved TV settings, maps the source path through `sonarrRoot`, and derives result paths only from `reviewRoot`, the configured TV `reviewPrefixes` and the source-relative path. The only extension mapping supported here is `.ts` or `.m2ts` to `.mkv`; other layouts remain unverified. It does not search for other files or show unrelated candidates.

A match requires exactly one current result file, a bounded version-1 `.tdarr-receipt.json` beside that result, and an explicit non-empty receipt `jobId`. Receipt source and output size, rounded modification time and first/last sample hash are compared to fresh reads of the selected source and result. Review then performs a bounded, read-only lookup for that exact job ID in the configured local Tdarr database and requires one successful row with the configured TV library ID, an exact configured source-root path, and source/result byte sizes matching the files. After re-fetching the Sonarr binding, Review repeats the bounded local check and compares private canonical file identities for the source, result, receipt and database, along with the receipt and job row. A changed binding, file, receipt, job or settings revision fails closed. These private identities are not returned to the browser. Rows over 64 KiB, duplicate IDs, older receipts without a job ID, changed files, unsafe paths and unsupported metadata are refused. Each isolated check has a 15 second deadline and reads at most 1 MiB from each end of the two media files; it does not decode or probe media and makes no Tdarr API call.

This is a **point-in-time association**, not an atomic snapshot or protection against later filesystem changes. It is not proof of output health, picture/audio quality, episode contents, human review, approval or permission to replace anything. The repository's sample receipt producer does not establish that an installed TV flow produces this receipt format. If local evidence or settings are missing or unsupported, the inspector reports an unverified reason. It does not enable TV processing, dispatch jobs, create receipts, save approvals or change media.

For the same one selected EpisodeFile, **Inspect technical facts** is an explicit follow-up action. It is available only when the exact current Sonarr binding, supported receipt, and one successful job for the configured TV library have been revalidated. Review probes the opened source and result files in an isolated bounded worker; it rechecks the complete private file, receipt, database and job evidence after probing. The probe is limited to supported container formats and the local file protocol, with external MOV references disabled. It cannot run when the association is missing, ambiguous, unsuccessful or belongs to another library. The request accepts only the saved settings revision and numeric series/file IDs; paths are derived server-side.

The display includes only allowlisted container and stream facts: duration, video codec, dimensions, frame rate and recognized color/HDR metadata, plus audio and subtitle codec, language and track flags. Values absent from the probe are shown as unknown. An absent HDR field is not evidence of SDR, and a reported HDR metadata marker does not prove that the content is preserved or looks correct. Unknown codecs and arbitrary tags are not displayed. Probe errors, raw metadata, private paths and credentials are not returned. Technical facts describe metadata only; they are not an integrity, decode, quality, episode-content, approval or replacement check. Unsupported media, malformed or oversized probe output, timeout, changed evidence and unavailable evidence remain unverified. No files or Tdarr database records are written.

Before saving or applying a Sonarr-enabled generation, make a private backup of Review's settings data. Older builds validate saved active settings against their own schema and do not recognize the added `active.sonarr` section; reverting code alone may therefore fail to load settings. A rollback to an older build requires restoring the matching private settings backup as well.

This is a manual read-only metadata and result-association check within #238. Broader disk inventory and reconciliation, previews, cohort review, replacement transactions, retention, pilot operation and Sonarr Recovery remain separate work and safety gates.
